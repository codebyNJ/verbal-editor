PRD

Product Requirements

1Problem

Rich-text editing on the web is solved badly at both ends. Hosted editors are closed and un-embeddable. Open editor frameworks are heavy and force their architecture onto the host app — a team adopting one inherits a dependency tree, a plugin API they did not choose, and a bundle that grows whether or not they use the features. A team building their own hits contenteditable and stops.

Realistic production bundle · gzipped KB
Plate / Slate120–180
Tiptap, feature-complete80–120
Tiptap + basics50–70
Lexical, real document40–60
Lexical core alone22
Verbal — full preset30
Verbal — core12
Oat UI — the bar10

Oat UI sets the reference: 7KB of CSS plus 2.9KB of JS, zero dependencies, semantic HTML styled without class soup. That is the weight class this editor targets, at Notion's feature set.

HLD

High-Level Design

3.1Design thesis

Three findings determine the entire architecture. Each one removes a dependency the field currently treats as mandatory, and together they are the reason a Notion-class feature set can fit in 30KB.

(a) For plain typing, do nothing

contenteditable and React fight over DOM ownership. Every keystroke mutates the DOM, and a re-render from state destroys the caret. The established resolution is that the editor owns the DOM and React only mounts hosts — but the stronger form is that on insertText and deleteContentBackward the editor also does nothing. The browser's insertion is already correct. Read the text back, update the model silently, write no DOM, render no component.

This is why zero re-renders per keystroke is achievable rather than aspirational: the fast path is an empty function.

(b) Syntax highlighting needs no DOM nodes

The CSS Custom Highlight API styles arbitrary Ranges without inserting a single element — shipped in Chrome and Edge 105, Safari 17.2, and Firefox 140 in June 2025. Code blocks become plain text nodes the caret traverses perfectly, with colour painted over the top. That eliminates the entire class of cursor bugs that makes code blocks in editable regions notoriously unstable, and the same primitive renders AI diffs, so two features share one mechanism.

(c) The browser already renders maths

MathML Core is natively supported across engines — Igalia upstreamed it into Chromium for Chrome 109, and Gecko and WebKit preceded it. The maths module is therefore a ~5KB compiler to MathML rather than a ~75KB gzipped renderer plus a font payload.

3.3Data model

A flat map plus child-order arrays, not a nested tree. Flat gives O(1) block lookup, ids that stay stable across moves, transactions that address a single block, and a payload that stays cheap to diff and patch as documents grow.

{
  "version": 1,
  "root": "doc",
  "blocks": {
    "doc": { "type": "doc", "children": ["b_1", "b_2"] },

    "b_1": { "type": "heading", "props": { "level": 1 },
             "content": [{ "text": "Ship it", "marks": [] }] },

    "b_2": { "type": "paragraph", "children": ["b_3"],
             "content": [
               { "text": "See ", "marks": [] },
               { "text": "the docs", "marks": [{ "type": "link", "href": "/docs" }] }
             ] }
  }
}

content is an inline run array, Notion's shape — marks live on runs rather than as nested nodes, so there is no mark tree to normalise. children handles all nesting, so toggle lists, nested bullets and column layout share one mechanism instead of three.

3.4Transaction model

Every operation carries the data needed to reverse it. Undo requires that regardless, so the collaboration-ready property costs nothing today.

{ op: 'insertText',  block: 'b_1', at: 7, text: 'now' }
{ op: 'deleteText',  block: 'b_1', at: 7, len: 3, text: 'now' }   // text kept for invert
{ op: 'setProps',    block: 'b_3', props: { checked: true }, prev: { checked: false } }
{ op: 'addMark',     block: 'b_1', from: 0, to: 4, mark: { type: 'bold' } }
{ op: 'insertBlock', parent: 'doc', index: 2, block: { /* … */ } }
{ op: 'moveBlock',   block: 'b_3', from: ['doc', 2], to: ['b_2', 0] }

invert(tx)          // → undo.          required now
rebase(tx, other)   // → collaboration. additive later, no redesign

3.5Rendering model

"Zero re-renders" cannot mean zero renders — mounting is a render. The enforceable definition, which becomes a CI gate rather than a claim:

  • 0 React renders per keystroke — typing, deleting, selecting, formatting.
  • Exactly 1 render, for the affected block only, on a structural change.
  • 0 renders for every other block in the document.

It works because the store exposes two notification paths and text edits use neither.

core/store.js
const versions = new Map();   // blockId → int
const subs     = new Map();   // blockId → Set<fn>

export const bump = (id) => {                // structural / prop change only
  versions.set(id, (versions.get(id) ?? 0) + 1);
  subs.get(id)?.forEach((fn) => fn());
};
export const silent = () => {};              // text edit: model updated, nobody told
react/index.js — a block subscribes to its own version and nothing else
export function useBlock(id) {
  const subscribe = useCallback((cb) => store.subscribe(id, cb), [id]);
  const version   = useSyncExternalStore(subscribe, () => store.version(id));
  return useMemo(() => store.get(id), [id, version]);
}
Why this holds

Typing never calls bump, so version never changes, so React is never told anything happened — and the DOM is already correct, because the browser wrote it.

3.6Module contract

Core ships knowing exactly one block type: paragraph. Everything else, headings included, arrives through this interface. It is what keeps core small while the feature list is long, and it is the entire surface a contributor has to learn.

blocks/heading/index.js
export default {
  type: 'heading',
  schema: { props: { level: [1, 2, 3] }, content: 'inline' },

  create: (props = {}) => ({ type: 'heading', props: { level: 1, ...props }, content: [] }),

  view: {
    create: (block) => document.createElement(`h${block.props.level}`),
    patch:  (el, block, prev) =>
      block.props.level !== prev.props.level ? null : el,   // null ⇒ recreate node
  },

  commands: {
    setLevel: (level) => (tx, blockId) => tx.setProps(blockId, { level }),
  },

  input: {
    markdown:  [[/^(#{1,3})\s$/, (m) => ({ type: 'heading', props: { level: m[1].length } })]],
    shortcuts: { 'Mod-Alt-1': 'setLevel(1)' },
  },

  slash:     { label: 'Heading 1', keywords: ['h1', 'title'], icon: 'H1' },
  parse:     { tags: ['h1', 'h2', 'h3'], markdown: /^(#{1,3})\s+(.*)$/ },
  serialize: { markdown: (b) => '#'.repeat(b.props.level) + ' ' + inline(b.content) },
};

A module folder is self-contained, and is the unit of work, review, documentation and size budget:

3.7Key flows

Keystroke — the hot path

beforeinput fires → insertText → return immediately, no preventDefault → the browser inserts the character → input fires → syncFromDom updates the model silently. Zero DOM writes, zero renders.

core/view.js
host.addEventListener('beforeinput', (e) => {
  switch (e.inputType) {
    case 'insertText':
    case 'deleteContentBackward':
      return;                                     // browser is right. do nothing.
    case 'insertParagraph':
      e.preventDefault();
      return editor.dispatch(splitBlock(e.getTargetRanges()[0]));
    case 'insertFromPaste':
      e.preventDefault();
      return editor.dispatch(parsePaste(e.dataTransfer));
    default:
      e.preventDefault();                           // unknown inputType never mutates
  }
});

InputEvent.getTargetRanges() supplies the exact ranges about to be affected before the mutation happens, which is what makes interception deterministic rather than inferred.

Enter

insertParagraph → prevented → splitBlock transaction → two bump calls → one render for the split block, one for the new one. Everything else in the document is untouched.

Paste

insertFromPaste → prevented → HTML and markdown parsed through each module's parse rules → sanitised → one insertBlock transaction. Raw HTML is never injected.

AI edit

The model response is built as a valid but uncommitted transaction, word-diffed against current content, and the hunks are painted with the Custom Highlight API over the real text. The document is untouched until accept; accept dispatches through the normal path, so an AI edit is undoable exactly like a typed one.

ai/pending.js
const pending = buildTx(aiResponse);                 // valid tx, not applied
const hunks   = diffWords(current, pending.preview());

accept(pending);   // → editor.dispatch(pending) → ordinary undo applies
reject(pending);   // → discard. model never knew.

Drag

Pointer Events track the block, a transform-based indicator shows the drop position, and release dispatches one moveBlock transaction.

3.9Cross-cutting design

Validation

Joi runs at trust boundaries only — document import, paste ingest, plugin config, the CLI config file, and the self-hosted server API. It is 56KB gzipped, five times Oat UI's entire library, and it never enters the client bundle. The editing path uses the plain schema object each module already declares.

Styling

Oat UI's method, not only its size: semantic tags styled contextually, so blocks render as <h1>, <blockquote>, <ul>, <table>, <code> with no class attribute in the common case. .module.css is colocated per module — scoped, dead-CSS-detectable, tree-shaken with its module. A single tokens.css of custom properties is the entire public theming API, with an automatic dark scheme.

Testing strategy

Two tools, for a technical reason rather than an aesthetic one. node:test covers core/: it is pure JS with no DOM, so the full model, transaction, history and selection surface runs with no environment and no dependency. Playwright covers view, blocks and performance.

Why not jsdom

jsdom implements neither getTargetRanges() nor a real Selection and Range model. Testing a contenteditable editor there would test the mock on precisely the behaviour that matters — so the DOM suite runs in real browsers across three engines, or it does not run.

test/perf/renders.spec.js — the gate that makes G-4 real
test('typing causes zero react renders', async ({ page }) => {
  await page.goto('/bench');
  await page.evaluate(() => (window.__renders = 0));
  await page.keyboard.type('the quick brown fox jumps over the lazy dog');
  expect(await page.evaluate(() => window.__renders)).toBe(0);
});

Size enforcement

About fifteen lines over zlib.gzipSync against a budget JSON. size-limit would be a dependency for something the standard library already does. It runs in the pre-commit hook and in CI, and it fails the build rather than warning.

Pre-commit

Git's own core.hooksPath pointed at a committed .githooks/ directory — no Husky, no node_modules indirection. The hook runs lint-on-staged, node --test test/core, and the size script. Playwright runs in CI only: a hook slow enough to be bypassed is a hook that does nothing.

Build and distribution

Vite library mode, ESM only, one entry per module, package.json#exports for subpaths, types generated from JSDoc, provenance-signed publish.
